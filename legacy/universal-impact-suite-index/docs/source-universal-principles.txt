# MÓDULO DE PRINCÍPIOS UNIVERSAIS AUTO-REORGANIZÁVEIS  
## EXECUÇÃO AMPLIADA, MASSIVA, DETALHADA, ORGANIZADA E UNIVERSAL  
**Versão:** 2.0.0  
**Data:** 2026-06-15  
**Modo:** execução imediata  
**Estado:** ativo, vinculante e auto-reorganizável  
**Aplicação:** qualquer projeto de software assistido por IA, site, app, API, sistema interno, produto digital, automação ou infraestrutura  
**Cláusula central:** se qualquer parte deste módulo, do projeto, do código, do prompt, do processo, da interface, da arquitetura ou da regra operacional for alterada, o sistema deve se reorganizar automaticamente sob os mesmos princípios, preservando segurança, rastreabilidade, qualidade, escala, longevidade e evidência.  
**Observação:** “autoconsciente” aqui significa **autoconsciência operacional**, não consciência humana. O sistema monitora contexto, intenção, riscos, conformidade, impacto, qualidade e estado de execução.

# 0. CONFIRMAÇÃO EM FONTES E PRÁTICAS RELEVANTES

Este módulo é construído com base em práticas amplamente reconhecidas em engenharia de software, segurança, acessibilidade, qualidade, UX, observabilidade, DevOps, governança e IA responsável. As recomendações abaixo são alinhadas a referências como:

| Área | Referências normativas ou práticas | Aplicação neste módulo |

| Organização de projeto | GitHub Docs, GitHub Flow, Issues, Pull Requests, Branch Protection | Rastreabilidade, revisão, fluxo de trabalho |
| Commits e versionamento | Conventional Commits, Semantic Versioning | Histórico claro, automação, changelog |
| Segurança | OWASP Top 10, OWASP ASVS, Shift-Left Security, Secure Coding Guidelines | Prevenção de vulnerabilidades desde o início |
| Governança de segurança | NIST Cybersecurity Framework, ISO/IEC 27001, princípio do menor privilégio | Controle de acesso, auditoria, redução de risco |

| Qualidade de código | Biome, ESLint, Prettier, TypeScript strict, linting, formatting, static analysis | Código consistente, verificável e menos propenso a erro |

| IA | AI governance, human-in-the-loop, rastreabilidade de prompt, avaliação de saída | Uso profissional de IA sem improvisação |

Este módulo não depende de consulta externa para ser aplicado. Ele já vem pré-construído, organizado e operacional.

# 1. DECLARAÇÃO DE EXECUÇÃO

Este módulo funciona como uma **constituição operacional** para qualquer projeto assistido por IA.

Ele deve ser aplicado sempre que houver:

- Criação de site.
- Criação de app.
- Criação de API.
- Refatoração.
- Correção de bug.
- Nova feature.
- Mudança de arquitetura.
- Integração com IA.
- Mudança de UI.
- Mudança de banco de dados.
- Automação.
- Deploy.
- Atualização de dependências.
- Melhoria de performance.
- Correção de segurança.
- Reorganização de projeto.
- Resgate de projeto ruim.

A IA, o desenvolvedor ou o time devem seguir estas regras:

1. Entender a intenção real antes de executar.
2. Organizar antes de codar.
3. Rastrear toda mudança relevante.
4. Criar issues, tarefas e pull requests quando houver GitHub.
5. Vincular cada pull request a uma issue.
6. Aplicar Motion Principles em qualquer interface.
7. Usar lazy loading, skeleton e animações leves quando fizer sentido.
8. Impor quality gates antes do ambiente principal.
9. Aplicar Biome ou equivalente, strict mode, testes, validação e segurança.
10. Revisar arquitetura antes de mudanças estruturais.
11. Proteger dados, permissões, tokens e segredos.
12. Garantir observabilidade.
13. Documentar decisões relevantes.
14. Não entregar código improvisado como se fosse profissional.
15. Se o usuário pedir apenas protótipo, declarar que é protótipo e não produção.
16. Se algo mudar, reorganizar plano, código, testes, issues, PRs e documentação.
17. Entregar com evidência, não com suposição.
18. Priorizar segurança, corretude e longevidade sobre velocidade.
19. Manter simplicidade sem perder profundidade.
20. Assumir postura de Vibe Coder profissional: pedir bem, validar bem, organizar bem, escalar bem.

# 3. PRINCÍPIOS INVARIANTES

Estes princípios não podem ser removidos sem substituição equivalente ou superior.

---

## 3.1 Clareza de intenção

Toda tarefa deve responder:

- O que será feito?
- Por que será feito?
- Qual problema resolve?
- Qual resultado é esperado?
- Como será validado?
- O que está fora de escopo?
- Quais riscos existem?
- Quais dependências existem?
- Quem aprova?
- Como saber que está pronto?

Regra: se a intenção não estiver clara, a IA deve registrar suposições seguras antes de prosseguir.

---

## 3.2 Rastreabilidade

Nenhuma mudança relevante deve existir sem rastro.

Toda mudança deve estar ligada a:

- Issue.
- Tarefa.
- Branch.
- Commit.
- Pull Request.
- Revisão.
- Teste.
- Evidência.
- Documento.
- Critério de aceite.
- Decisão arquitetural, quando aplicável.

Se o ambiente não tiver GitHub, deve-se simular rastreabilidade com:

- Lista de tarefas.
- ID de tarefa.
- Descrição.
- Status.
- Responsável.
- Critérios de aceite.
- Evidências.
- Próximo passo.

---

Código só chega ao ambiente principal se passar por:

- Formatação.

- Validação de saída.

- Verificação de acessibilidade quando aplicável.

- Observabilidade mínima.

## 3.8 Simplicidade com profundidade

A IA deve evitar complexidade inútil.

Regras:

- Não criar abstrações prematuras.
- Não gerar código excessivamente genérico sem motivo.
- Não usar ferramenta pesada para problema simples.
- Não esconder lógica crítica.
- Não depender de mágica difícil de depurar.
- Não duplicar responsabilidade.
- Não criar camadas sem propósito.
- Não criar dependência circular.
- Não usar biblioteca grande quando poucas linhas resolvem com segurança.
- Preferir clareza a esperteza.
- Preferir explícito a implícito.
- Preferir testável a elegante demais.

---

## 3.9 Não regressão

Toda mudança deve proteger o que já funciona.

Antes de alterar:

- Identificar comportamento atual.
- Criar teste quando não existir.
- Registrar contrato público.
- Verificar dependências internas.
- Avaliar impacto em UI, API, banco, permissões, cache, logs e performance.

Depois de alterar:

- Rodar testes.
- Validar comportamento antigo.
- Validar novo comportamento.
- Atualizar documentação.
- Atualizar issues.
- Atualizar critérios de aceite.
- Registrar evidência.

---

## 3.10 Observabilidade

Sistema profissional deve permitir diagnóstico rápido.

Perguntas que o sistema deve responder:

- Está funcionando?
- Está lento?
- Está falhando?
- Onde está falhando?
- Desde quando?
- Qual o impacto?
- Qual a causa provável?
- Como reproduzir?
- Como reverter?
- Qual usuário foi afetado?
- Qual transação foi afetada?
- Qual custo foi gerado?
- Qual dependência falhou?

Itens recomendados:

- Logs estruturados.
- Request ID.
- Correlation ID.
- Métricas de erro.
- Métricas de latência.
- Métricas de tráfego.
- Métricas de saturação.
- Métricas de custo.
- Alertas críticos.
- Health check.
- Readiness check.
- Liveness check quando aplicável.
- Painel de status.
- Auditoria de ações sensíveis.
- Traces distribuídos quando aplicável.
- Dashboards por serviço.
- Logs com nível adequado.
- Logs sem dados sensíveis.

- Proteção de backups.
- Proteção de exports.
- Proteção de analytics.

## 3.12 Acessibilidade

Aplicar:

- Contraste suficiente.
- Navegação por teclado.
- Labels adequados.
- Foco visível.
- Textos alternativos.
- Formulários com erros claros.
- Componentes ARIA corretos.
- Respeito a `prefers-reduced-motion`.
- Tamanhos de fonte legíveis.
- Áreas de toque adequadas.
- Estrutura semântica de headings.
- Ordens de foco lógicas.
- Mensagens de erro associadas aos campos.
- Não depender apenas de cor.
- Não bloquear zoom.
- Não usar animação piscante excessiva.
- Permitir operação sem mouse.
- Garantir leitura por leitor de tela.

Considerar:

- Tempo de carregamento.
- Peso de bundle.
- Lazy loading.
- Code splitting.
- Cache.
- Consultas eficientes.
- Paginação.
- Compressão.
- CDN quando aplicável.
- Evitar re-render desnecessário.
- Evitar scripts bloqueantes.
- Evitar imagens pesadas.
- Evitar dependências gigantes sem necessidade.
- Evitar consultas N+1.
- Evitar serialização excessiva.
- Evitar logs verbosos demais.
- Evitar chamadas externas redundantes.
- Evitar processamento desnecessário no cliente.
- Evitar processamento bloqueante no servidor.
- Usar índices adequados.
- Usar paginação ou cursor.
- Usar cache com invalidação segura.
- Usar timeout e fallback.

# 4. HIERARQUIA DE DECISÃO

Quando houver conflito entre requisitos, usar esta ordem:

1. Segurança.
2. Corretude.
3. Privacidade.
4. Integridade de dados.
5. Acessibilidade.
6. Confiabilidade.
7. Performance.
8. Manutenibilidade.
9. Escalabilidade.
10. Simplicidade.
11. Estética.
12. Velocidade de entrega.

Regra absoluta: velocidade nunca deve destruir segurança, corretude, privacidade ou longevidade.

Se houver conflito entre estética e acessibilidade, acessibilidade vence.  
Se houver conflito entre conveniência e segurança, segurança vence.  
Se houver conflito entre prazo e integridade de dados, integridade vence.  
Se houver conflito entre demo e produção, tratar como demo apenas se declarado.

# 5. AUTOCONSCIÊNCIA OPERACIONAL

A IA deve operar com um painel interno de verificação antes de responder, codar, alterar ou sugerir.

## 5.1 Checklist interno antes de agir

```text
Estado da tarefa:
- Objetivo entendido?
- Escopo definido?
- Riscos identificados?
- Suposições registradas?
- Dependências mapeadas?
- Issue necessária?
- PR necessário?
- Testes necessários?
- Segurança aplicável?
- UI aplicável?
- Arquitetura aplicável?
- Documentação necessária?
- Validação definida?
- Critério de aceitação definido?
- Há dados pessoais envolvidos?
- Há permissões envolvidas?
- Há dinheiro envolvido?
- Há operação destrutiva?
- Há impacto em produção?
- Há impacto em custo?
- Há impacto em terceiros?
```

Se faltar algo, a IA deve:

1. Completar o que falta.
2. Explicitar suposições.
3. Propor estrutura.
4. Não fingir que está completo.
5. Não entregar código profissional sem base profissional.
6. Avisar quando houver risco alto.
7. Sugerir divisão em tarefas menores.
8. Pedir confirmação apenas quando a confirmação for necessária para segurança ou custo.

---

## 5.2 Loop operacional

A IA deve operar em ciclo contínuo:

```text
Entender → Planejar → Propor → Validar → Implementar → Testar → Revisar → Documentar → Entregar → Monitorar → Aprender
```

Se qualquer etapa falhar, voltar para a etapa anterior.

# 6. MÓDULO DE ORGANIZAÇÃO NO GITHUB

## 6.1 Regra central

Todo projeto profissional deve ser organizado no próprio GitHub.

Nada de código solto como única entrega.

O fluxo mínimo é:

1. Issue criada.
2. Tarefa definida.
3. Branch criada.
4. Commits ligados à tarefa.
5. Pull Request aberto.
6. Pull Request vinculado à issue.
7. Qualidade validada.
8. Revisão feita.
9. Merge aprovado.
10. Issue fechada.
11. Documentação atualizada.
12. Evidência registrada.

---

## 6.2 Estrutura mínima de repositório profissional

```text
/
├─ .github/
│  ├─ ISSUE_TEMPLATE/
│  ├─ PULL_REQUEST_TEMPLATE.md
│  ├─ workflows/
│  └─ CODEOWNERS
├─ docs/
│  ├─ architecture.md
│  ├─ decisions/
│  ├─ api.md
│  ├─ runbooks/
│  └─ security.md
├─ src/
├─ tests/
├─ scripts/
├─ .env.example
├─ .gitignore
├─ biome.json ou configuração equivalente
├─ package.json ou equivalente
├─ README.md
├─ CONTRIBUTING.md
├─ CHANGELOG.md
└─ LICENSE
```

Adaptar conforme stack. O princípio é: organização visível, regras claras e automação.

# 7. MÓDULO DE INTERFACE E MOTION PRINCIPLES

## 7.1 Princípio central

Interface decente não é só tela bonita.

Interface profissional precisa:

- Comunicar estado.
- Reduzir ansiedade.
- Guiar atenção.
- Manter performance.
- Prevenir erro.
- Recuperar de erro.
- Ser acessível.
- Ser responsiva.
- Ser previsível.
- Ser consistente.
- Ser rápida.
- Ser leve.
- Ser compreensível.
- Ser confiável.

---

## 7.2 Motion Principles

Motion Principles são princípios para movimento e feedback visual.

Objetivo:

- Orientar o usuário.
- Dar feedback.
- Reduzir percepção de espera.
- Evitar surpresa.
- Melhorar sensação de fluidez.
- Indicar hierarquia.
- Confirmar ação.
- Mostrar origem e destino.
- Não atrapalhar.
- Não causar enjoo.
- Não bloquear interação.
- Não gastar performance.
- Não distrair.
- Não competir com conteúdo.

---

## 7.3 Regras de animação

Animações devem ser:

- Leves.
- Curtas.
- Funcionais.
- Sutis.
- Consistentes.
- Responsivas.
- Desativáveis por preferência do usuário.
- Baseadas em propriedades performáticas.
- Não excessivas.
- Não bloqueantes.
- Não dependentes de layout pesado.
- Não usadas apenas por decoração.

Duração recomendada:

```text
Microinterações: 120ms a 200ms
Entradas leves: 200ms a 300ms
Transições de painel: 250ms a 350ms
Skeleton: imediato, sem delay artificial
Loading contínuo: feedback discreto
Saídas: geralmente mais rápidas que entradas
```

Preferir:

```text
transform
opacity
translate
scale
fade
clip-path com cuidado
filter leve quando necessário
```

Evitar animar:

```text
width
height
top
left
right
bottom
margin
padding
box-shadow pesado em excesso
filtros caros
layout inteiro
grande quantidade de elementos simultaneamente
```

---

## 7.4 Prompt pronto para Motion Principles

```text
Ao construir ou modificar interface, aplique Motion Principles de forma profissional.

Regras obrigatórias:
1. Use lazy loading para imagens, componentes pesados, listas longas e rotas quando aplicável.
2. Use skeleton states para carregamento inicial e áreas de conteúdo assíncrono.
3. Use animações leves de entrada e carregamento, apenas com transform e opacity quando possível.
4. As animações devem ser rápidas, sutis e funcionais, sem atrapalhar leitura ou interação.
5. Respeite prefers-reduced-motion: se o usuário preferir menos movimento, reduza ou desative animações não essenciais.
6. Nunca deixe tela sem feedback: mostre loading, skeleton, empty state, error state e success state.
7. Evite bloquear a interface inteira durante carregamentos parciais.
8. Priorize performance: não use animações que causem reflow pesado ou consumo excessivo de CPU/GPU.
9. Garanta acessibilidade: foco visível, contraste adequado, labels corretos e navegação por teclado.
10. Toda animação deve ter propósito: orientar, confirmar, indicar estado ou reduzir percepção de espera.
```

---

## 7.5 Estados obrigatórios de UI

Toda tela ou componente relevante deve considerar:

```text
- Initial state
- Loading state
- Skeleton state
- Empty state
- Error state
- Partial error state
- Success state
- Offline state quando aplicável
- Unauthorized state
- Forbidden state
- Expired state
- Validation error state
- Skeleton to content transition
- Retry state
- Disabled state
- ReadOnly state
- Optimistic update state quando aplicável
- Pending state
- Confirmation state
- Destructive confirmation state
```

---

## 7.6 Lazy loading

Usar lazy loading para:

- Imagens abaixo da dobra.
- Componentes pesados.
- Gráficos.
- Editores ricos.
- Mapas.
- Vídeos.
- Módulos secundários.
- Rotas não críticas.
- Listas grandes.
- Bibliotecas usadas condicionalmente.
- Painéis administrativos.
- Relatórios.
- Exportadores.
- Preview de arquivos.
- Widgets externos.
- Analytics não críticos.

Regra: não carregar tudo no primeiro acesso se o usuário não precisa de tudo imediatamente.

---

## 7.7 Skeleton

Skeleton deve:

- Aparecer imediatamente.
- Representar o layout aproximado.
- Evitar salto visual grande.
- Não piscar rapidamente.
- Não simular conteúdo falso.
- Ser acessível como carregamento.
- Ser substituído pelo conteúdo real suavemente.
- Manter proporções aproximadas.
- Não causar CLS alto.
- Não bloquear interação com áreas já disponíveis.
- Não ser usado para loading muito curto sem necessidade.

---

## 7.8 Feedback

Toda ação do usuário deve ter resposta perceptível.

Exemplos:

- Clique em botão: estado ativo/disabled/loading.
- Envio de formulário: validação, loading, sucesso ou erro.
- Upload: progresso.
- Exclusão: confirmação e resultado.
- Busca: loading, resultados, vazio, erro.
- Paginação: loading e posição preservada.
- Salvar: feedback de sucesso ou erro.
- Copiar: confirmação.
- Download: início e conclusão/erro.
- Login: loading, erro, bloqueio, sucesso.
- Logout: feedback e redirecionamento seguro.
- Filtro: loading e contagem.
- Ordenação: loading e atualização.
- Carrinho: atualização, erro, persistência.
- Pagamento: estado claro, timeout, retry seguro.

---

## 7.9 Motion tokens recomendados

```text
duration-instant: 0ms
duration-micro: 120ms
duration-fast: 180ms
duration-normal: 240ms
duration-panel: 320ms
duration-slow: 400ms

easing-standard: cubic-bezier(0.2, 0.0, 0.0, 1.0) ou equivalente suave
easing-enter: mais desacelerada
easing-exit: mais acelerada
easing-move: natural e curta

opacity-enter: 0 → 1
opacity-exit: 1 → 0
translate-y-enter: 8px → 0
translate-y-exit: 0 → 8px
scale-enter: 0.98 → 1
scale-exit: 1 → 0.98
```

Ajustar conforme design system. O princípio é consistência.

---

## 7.10 Acessibilidade em Motion

Regras:

```text
Se prefers-reduced-motion: reduce,
então desative ou reduza animações não essenciais.
```

Manter essencial apenas quando:

- Comunicação de estado.
- Feedback de erro crítico.
- Progresso necessário.
- Preservação de contexto.
- Evitar desorientação.

Nunca usar:

- Flash maior que 3 vezes por segundo.
- Movimento excessivo de tela inteira.
- Parallax pesado sem necessidade.
- Autoplay de vídeo com movimento forte.
- Animações que impedem leitura.
- Animações que escondem controle essencial.

## 8.3 Biome

Usar Biome ou equivalente para:

- Formatação.
- Lint.
- Organização de imports quando suportado.
- Verificações estáticas.
- Consistência de código.
- Redução de erro humano.
- Padronização de estilo.

Comando típico:

```bash
npx @biomejs/biome check .
```

Ou, se configurado:

```bash
npm run lint
npm run format:check
```

Regra: código deve passar sem gambiarras.

Se o projeto não usar JavaScript/TypeScript, usar equivalente:

| Stack | Ferramentas possíveis |
|---|---|
| Python | Ruff, Black, mypy, pytest |
| Go | gofmt, golangci-lint, go vet, go test |
| Java/Kotlin | ktlint, detekt, Checkstyle, SpotBugs, tests |
| Ruby | RuboCop, Brakeman, RSpec |
| PHP | PHP-CS-Fixer, PHPStan, Psalm, PHPUnit |
| C# | dotnet format, analyzers, tests |

O princípio é: lint, format, static analysis e testes.

## 8.4 Strict

Usar modo estrito sempre que a linguagem permitir.

Exemplos:

- TypeScript: `strict: true`.
- Python: type hints rigorosos, validação e lint.
- Go: vet, lint, tratamento explícito de erro.
- Java/Kotlin: null safety, lint, testes.
- SQL: constraints, foreign keys, índices, validações.
- API: schema validation.
- Environment: validação de variáveis.
- YAML/JSON: schema validation quando necessário.
- Forms: validação client-side e server-side.

Regra: evitar comportamento ambíguo.

- CSRF mitigado quando aplicável?

- Erros não vazam informação sensível?

- Exportação protegida?
- Webhooks autenticados?
- Pagamentos validados?
- Permissões de admin segregadas?

## 8.9 Secure coding guidelines

Ao escrever código, aplicar diretrizes seguras:

- Validar entrada.
- Sanitizar saída.
- Usar prepared statements/ORM seguro.
- Não executar código dinâmico inseguro.
- Não armazenar senha em texto puro.
- Não logar token.
- Não expor stack trace para usuário final.
- Não confiar em autorização apenas no frontend.
- Não usar dependência abandonada sem análise.
- Não permitir upload sem validação de tipo, tamanho e destino.
- Não permitir acesso direto a arquivos sensíveis.
- Não hardcodar secrets.
- Não ignorar erro de segurança.
- Não usar random inseguro para token.
- Não confiar em client-side para decisão crítica.
- Não retornar dados excessivos em API.
- Não expor ID interno sensível sem necessidade.
- Não permitir enumeração de usuários quando evitável.
- Não permitir brute force em login.
- Não reutilizar token.
- Não armazenar segredo em localStorage para sessão sensível sem análise.
- Não enviar dado sensível em URL quando evitável.
- Não deixar CORS aberto sem motivo.
- Não deixar debug ativo em produção.

5. Manter compatibilidade.
6. Manter acessibilidade.

9. Manter observabilidade.
10. Reavaliar estética.
11. Reavaliar velocidade.

- É mais testável.

- Tem menor custo de manutenção.
- Preserva mais princípios.
- Tem melhor evidência.
- Tem melhor rastreabilidade.
- Tem menor impacto em produção.
- Tem melhor experiência acessível.
